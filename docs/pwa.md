# Offline-first PWA · этап 11

## Установка на iPhone

1. Откройте HTTPS-адрес Reedit в Safari. HTTP разрешён только для разработки на localhost.
2. «Поделиться» → «На экран “Домой”» → «Добавить». Если есть переключатель открытия как веб-приложения, оставьте его включённым. [Официальная инструкция Apple](https://support.apple.com/ru-ru/guide/iphone/iphea86e5236/ios).
3. Откройте установленное приложение с интернетом. В Настройках дождитесь готовности офлайн-режима, затем импортируйте собственные книги. Если хранилища Safari и установленного приложения различаются, перенесите библиотеку через ZIP, не очищая сайт.
4. Проверьте открытие в авиарежиме после закрытия приложения. Первая установка требует сети; внешние каталоги офлайн недоступны.

Manifest задаёт стабильный id, имя Reedit, standalone, scope, start_url и русскую локаль. PNG 192/512, maskable 512 и apple-touch-icon 180 созданы из собственной геометрической пиктограммы, без материалов Apple. Исходники: public/icons/icon.svg, build/icons.ts.

## Кэш и обновления

SW включён только в production. Vite writeBundle читает **окончательные байты** HTML/JS/CSS, всех ленивых модулей (включая читалку и backup codec), manifest и иконок. SHA-256 и уникальный build id внедряются в sw.js. Расчёт до последних преобразований Vite недопустим; регрессию проверяет production-тест.

Install создаёт `reedit-shell-<build>` и проверяет каждый ответ и SHA. Сеть, квота или смешанный deployment могут отклонить установку: тогда удаляется только незавершённый **новый кэш**, предыдущий worker остаётся рабочим. Worker не обращается к IndexedDB и не очищает её.

Навигация получает index.html закреплённой версии из кэша. Статические файлы из build allowlist — cache-first. `/api/`, внешние запросы, книги, пользовательские обложки и blob URL в Cache Storage не помещаются. EPUB/FB2 и пользовательские данные находятся в IndexedDB. Старые hashed JS/CSS могут обслуживаться из сохранённого кэша своей версии для поздних импортов старой вкладки.

Новый worker остаётся waiting без автоматического skipWaiting/перезагрузки книги. В Настройках есть проверка и явное применение обновления. Worker разрешает активацию только единственному инициирующему окну вне читалки. При других окнах просит их закрыть. Применение блокирует переходы диалогом; перезагружается только инициировавшая страница. Обычный controllerchange не перезагружает читающего пользователя. После естественного закрытия всех старых окон следующая версия активируется штатно.

Старые shell-кэши очищаются только когда единственная страница подтверждает build id текущего worker. При нескольких вкладках/несовпадении версии они сохраняются. Очистка ограничена префиксом Reedit, не затрагивает другие кэши или БД. Сервер отдаёт sw.js/HTML/manifest с no-cache; регистрация использует updateViaCache:none. [Жизненный цикл Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers), [Chrome lifecycle](https://developer.chrome.com/docs/workbox/service-worker-lifecycle).

## Место на устройстве

Настройки показывают estimate(), предупреждают при заполнении более 85% и предлагают явный запрос persist(). Отсутствие API или отказ не блокирует чтение. QuotaExceededError обрабатывается хранилищем; восстановление откатывает транзакцию, а неполный новый shell не активируется.

Оценка квоты приблизительна; положительный persist() не защищает от очистки сайта, удаления приложения или потери устройства. WebKit описывает Storage API и эвристику persist начиная с Safari 17: [Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/). На целевом Safari 16.4 используются только доступные API, без предположения наличия persist().

## Проверка и выпуск

`pnpm test:pwa` собирает production и запускает отдельный сервер из tests/pwa, который не входит в dist. Проверяются финальные SHA, ZIP UI/подтверждение, настоящий SW, повторный запуск браузера с прежним дисковым профилем **без сети**, книга/позиция и ранее не посещённые ленивые разделы, waiting во время чтения, другие окна, применение обновления и отказ версии с нарушенной целостностью.

Ручная приёмка: установка из Safari, standalone/иконки/safe-area, выключение и включение iPhone в авиарежиме, фон/блокировка, несколько окон Safari/PWA, нехватка места, обновление при открытой книге и ZIP из «Файлов». Chromium не заменяет физическое устройство. Автономный запуск после закрытия браузера автоматизирован; перезагрузка реального устройства — ручная.

Развёртывание и релиз не выполнялись. Успешное восстановление и ручная iPhone-приёмка обязательны до выпуска.

Итоговый production-набор: 10 сценариев успешно на Chromium desktop/mobile. В том числе отдельная проверка гонки: после разрешения активации пользователь возвращается к книге системной навигацией. Обработчик controllerchange повторно проверяет маршрут и не перезагружает открытую читалку; проверяются сохранение позиции и отсутствие нового document load. Тест ждёт подтверждённой фазы применения обновления, а сервер моделирует задержку активации. Обычный полный регрессионный набор — 85 успешно, один desktop skip для touch; доменные/интеграционные тесты — 165 успешно.
